- **Fixed**: a checkpoint could drop the operation record of a write that had committed but not yet completed. The record's WAL pin drops once its update reaches a root's data file, so the head could pass the record before `Complete` marked the slot done. The snapshot left the slot out (not done) and replay no longer had the record, so a retry after a crash ran the write twice. A persistent write now tells the operation table just before it commits, and the checkpoint head is taken no higher than the lowest such write's WAL position until it completes. The checkpoint format is unchanged. A new `operation_table.test` case takes the checkpoint in that gap and checks the retry gets the saved outcome (#861).

- **Fixed**: an fsync (or write) error while the file service was recording a file-map change ended its runner fiber, and every later file-map change, durable save and the shutdown that waited on them hung forever. The ops in flight now complete with a disk error, and the file service refuses every later file-map change with an error until a restart: after a failed fsync, nothing written to that device since its last good sync can be trusted to be on disk, so neither retrying nor carrying on is safe. Reads keep working from the in-memory map, a removal that failed puts its file back so its blocks stay allocated, and a restart reloads the map from what reached the disk. The durable writer and merger no longer die on such an error either: they stop writing, keep saves readable in memory as they do on a full disk, and report it through `TDurableManager::HasFailed()` (#621).

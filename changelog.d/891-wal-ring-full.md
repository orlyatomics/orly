- **Fixed**: a safe root under sustained write load could hang for good once the WAL ring filled (#891). Ring space was checked only when the WAL leader came to write a record, after its transaction had already been applied, so a record could be queued with no room behind it; the root flush then waited for that record to be durable (write-ahead, #755), the checkpoint that would make room waited for the flush, and the leader waited for the checkpoint. A safe transaction now reserves its record's room in the ring before it applies anything, and the WAL counts every record it has taken but not yet written, so a record it accepts always has room. A client write the ring can't take is refused with `"status": "insufficient_storage"` (retryable, nothing written) and accepted again once a flush and checkpoint free room. Client writes and new POVs leave an eighth of the ring free for the server's own writes (promotion, pause and unpause), so those keep going and drain the backlog. `wal.test` reproduces the hang (it hung on master) and now checks that a full ring refuses rather than strands a record. A pause or unpause may use that eighth too, so unpausing the POV whose backlog filled the ring is not itself refused. A client write whose record is more than half that eighth is refused with `"status": "write_too_large"` (split it, or raise `--wal_mb`), since its promotion could never be sure of room. A slave applying replicated records waits for a checkpoint to free room rather than refusing, so a replicated batch is never left half applied; it gives up only when replication or the server stops. Writes the server makes on a client's behalf (opening a POV's repo, recording an index or an installed package) are refused with `insufficient_storage` too, not a generic error.

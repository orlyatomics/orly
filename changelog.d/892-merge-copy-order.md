- **Fixed**: the memory-layer merge copied each update by adding its entries in memory-layer order, which is (index id, key, seq), while an update keeps its entries ordered by key alone and finds each one's place walking back from the tail. For an update spanning several indexes that made the copy quadratic, and under sustained 4,096-op batches it took about 40% of the server's CPU, so the merge could not keep up, the Update Entry pool filled and writes were refused (`StepMergeMem out of pool space; merge rolled back`). Both copy paths in `StepMergeMem` now go through `TMemoryLayer::ImporterAppendCopies`, which adds the entries in key order (a stable sort, so equal keys in different indexes keep their order) and then links them into the new layer in the original order. Mutators are still carried over, and nothing is linked until every copy has been made, so running out of pool space still leaves the repo as it was. New `memory_layer.test` cases check the copy's entries, order and mutators, and time it against the old order (4,096 entries over 8 indexes: about 40 ms before, 1.6 ms now) (#892).

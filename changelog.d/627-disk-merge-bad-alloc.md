- **Fixed**: a disk merge that runs out of pool space no longer aborts `orlyi`. Before, any `std::bad_alloc` in `TSafeRepo::StepMergeDisk` (or `StepTail`) reached its outer catch and called `abort()`. Each of the three allocations a disk merge makes now recovers. The fold step, which builds an update and an entry for every key of the merged file in the update pools, keeps the merge unfolded when it can't get them: the unfolded file is a correct result, as on the merge's fast path, and folding only bounds read amplification. The merged file's disk layer comes from the Data Layer pool before the file is written, and if it can't be had the merge hands its inputs back and retries after a backoff, as it does for a full disk (#590). Publishing the merge builds a mapping from the mapping pools. If that fails, the half-built mapping is deleted, the merged file (which no reader has seen) is removed, and the inputs are handed back for a retry. `StepTail` does the same, without the retry. A new unit test in `orly/indy/repo.test.cc` fills each pool in turn before a merge that has a `+=` to fold. Before the fix, each case aborted the test; now every one reads back correctly and merges once the pool has room (#627).

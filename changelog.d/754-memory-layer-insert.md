- **Fixed (performance)**: writing keys that don't arrive in key order (uuids, hashes, anything random) no longer slows down in proportion to how much the memory layer already holds. A memory layer insert found its place by walking back from the layer's tail, so an entry that belonged in the middle walked about half the layer: a 4,096-key batch of random keys took 400 to 1,000 ms once the layer held 20k to 80k entries, against about 25 ms in key order, and a full layer cost O(n²) to build. The insert now finds its place through the skip list's express lanes (the ones point reads already seek through) in O(log n), and an entry at or past the tail is still appended in O(1), now without the lane descent it used to make too. The layer's order is unchanged, ties included. The disk merge's fold, which rebuilt its output the same way, now also inserts its updates in sequence order, so its update list doesn't walk from the tail either. A new smoke (`clients/smoke/run-insert-order.sh`) times in-order and random batches and prints METRIC lines for ab-bench (#754).

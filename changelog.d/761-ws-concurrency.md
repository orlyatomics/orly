- **Changed (performance)**: WebSocket statements no longer hold an I/O thread while they run, so WebSocket throughput scales with sessions and cores instead of stopping at `--num_ws_threads` (default 4) divided by one statement's latency. A try, batch or multi is parsed on the I/O thread, then runs on a fiber on the fast runners (the ones the binary protocol's statements run on), and its reply is sent from the connection's strand when it's done; the single websockets runner now only serves setup statements (`new session`, `install`, `new pov`, ...). A connection still has at most one statement in flight, so each session's statements run in order, and back-pressure, auth, the read budget and graceful shutdown (which waits for statements in flight, as it waited for the I/O threads) are unchanged. A new flag, `--max_ws_in_flight`, bounds how many run at once (default `max_parallel_frames / 8`, at least 4); the rest wait in arrival order. A new smoke, `clients/smoke/run-ws-scale.sh`, prints reads/s and p50/p99 of point and prefix reads at 1, 3, 16, 64 and 256 sessions as METRIC lines, and CI checks that with one I/O thread 16 sessions read several times faster than one (#761).

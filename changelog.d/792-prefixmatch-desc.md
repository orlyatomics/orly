- **Fixed (correctness, wrong read results)**: a `keys` walk or point read whose pattern has a member with no quick comparison (a `desc` member, a nested tuple, a list) before a free member returned nothing once its keys were on disk. `keys (int) @ <['d', desc g, free::(int)]>` gave `[]` from a release `orlyi` as soon as the global repo merged to a disk file, and a debug `orlyi` aborted on the disk walker's cross-check assert. `Atom::TCore::PrefixMatch`, which the walker uses to match each key on disk, fell back to comparing the whole pattern with the whole key when it couldn't compare one member quickly, and the pattern's free member never equals the key's value there. It now compares just that member, and defers to the reference matcher when the members differ, so a free nested inside a member still unifies. The bug predates v0.2.0. A new `orly/indy/prefix_match.test` checks `PrefixMatch` against `MatchPrefixState` for desc members, mixed ascending and descending members, nested tuples, strings, blobs and lists, and a new smoke, `clients/smoke/run-desc-prefix.sh`, runs in the debug and release CI jobs: it reads such keys from memory and again from disk (#792).

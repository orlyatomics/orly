# Changelog

All notable changes to Orly.

Entries reference the originating pull request and the closed issue where applicable. Format loosely follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and versions follow [Semantic Versioning](https://semver.org/) with the pre-1.0 caveat that the orlyscript language, the wire protocol and the on-disk format may still change between minor versions. In-repo work lands as a fragment in `changelog.d/`; `tools/fold_changelog.py` folds them into `[Unreleased]`, and cutting a release moves that section under a version heading.

## [v0.2.0] — 2026-10-06

A robustness release. Under memory or disk pressure `orlyi` now refuses writes instead of aborting, and keeps
serving reads: memory admission holds a merge reserve in the update pools (#607), disk admission holds a
reserve on the volumes (#590), each POV's writer backlog is capped before the write commits (#721), and the
memory budget follows a container's limit (#669). A per-read budget stops a runaway query before it exhausts
memory (#694). Merges and Tetris promotion lose a run of crashes, deadlocks and wrong-value bugs, among them
duplicate keys in release disk merges (#666), a merge running on a destroyed repo (#614) and an unpause
segfault (#633). Listeners bind to loopback by default, remote compile is off by default (#705), and an
optional shared secret guards clients and replication (#710). A reopened store is checked for consistency
at open (#700), and `orlyi` itself now runs under ThreadSanitizer in CI (#713). Batches can mix methods (#255).

### Upgrading from 0.1.x

- **Remote clients need `--bind_address`.** On a bare host the client (19380), WebSocket (8082) and
  reporting (19388) listeners bind `127.0.0.1`. Start `orlyi` with `--bind_address=0.0.0.0` (or one
  interface's address) if clients, a balancer or monitoring connect from another machine. The replication
  listener still binds every interface; `--slave_bind_address` narrows it. The Docker image binds every
  interface inside the container, so `docker run -p` works as before ([#705](https://github.com/orlyatomics/orly/issues/705)).
- **`compile` over WebSocket is off.** It is refused with `"status": "remote_compile_disabled"` unless
  `orlyi` is started with `--allow_remote_compile`. `orlyc` plus `install` is unchanged ([#705](https://github.com/orlyatomics/orly/issues/705)).
- **Upgrade a master and its slave together.** A durable save's ttl now replicates as a duration, so a
  0.1.x server and a 0.2.0 server paired either way disagree about it ([#676](https://github.com/orlyatomics/orly/issues/676), PR [#688](https://github.com/orlyatomics/orly/pull/688)).
- **New refusals clients may see.** Each has a dedicated error type in the 0.2.0 TS, Python and Go clients.
  - `insufficient_memory` (retryable): a write that would dip into the update pools' merge reserve,
    `--memory_reserve_pct` (default 25; 0 turns it off) ([#607](https://github.com/orlyatomics/orly/issues/607)). Also a write to a paused or failed POV whose
    backlog is at its cap ([#626](https://github.com/orlyatomics/orly/issues/626)), and a writer whose POV backlog has not shrunk for 5 s ([#721](https://github.com/orlyatomics/orly/issues/721)).
  - `insufficient_storage` (retryable): free disk below the reserve, `--disk_reserve_mb`, else
    `--disk_reserve_pct` (default 10; both 0 turns it off) ([#590](https://github.com/orlyatomics/orly/issues/590)).
  - `write_too_large` (not retryable; split the batch): one write with more entries than half the Update
    Entry pool's merge reserve ([#687](https://github.com/orlyatomics/orly/issues/687)).
  - `read_too_large` (not retryable as sent): a method call past the per-read budget, by default a
    sixteenth of the memory budget (at least 16 MiB, `--read_budget_mb`) and one row per 256 bytes of that
    (`--read_budget_rows`); `--read_budget_mb=0` turns it off ([#694](https://github.com/orlyatomics/orly/issues/694)).
- **Optional shared-secret auth** is off by default, and without a token the wire bytes are unchanged. To
  turn it on, give the token to every client first, then restart the slaves with it, then the master;
  anything without it is refused from then on ([#710](https://github.com/orlyatomics/orly/issues/710)).
- **A store with corrupt block accounting refuses to open.** If a block a live file owns is free or
  pending discard, or a block has two owners, `orlyi` stops at open instead of risking writes over live
  data; `--open_check=false` skips the check to recover such a store. Leaked blocks and overlapping
  sequence ranges are only logged ([#700](https://github.com/orlyatomics/orly/issues/700)).
- **Memory is sized from a budget.** It is the smaller of free RAM and the cgroup limit, or
  `--memory_budget_mb`; `orlyi` refuses to start when that cannot fund its minimum working set. Without a
  limit the sizes on a bare host are unchanged. The image plans for 4 GiB unless limited
  (`ORLY_MEMORY_BUDGET_MB`) and no longer pins 4,000 fiber frames, so by default it runs fewer requests
  at once; `--max_parallel_frames` still sets the count ([#669](https://github.com/orlyatomics/orly/issues/669)).
- **The global POV's disk merges drop superseded versions.** Each key keeps its current version, and a `+=`
  chain keeps its history. `--prune_merge_history=false` keeps everything; `--allow_tailing` now gates only
  the `tail` statement. Pruned history cannot be recovered by downgrading, though older binaries read the
  files ([#592](https://github.com/orlyatomics/orly/issues/592)).
- **Clients:** the 0.1.x TS and Python clients' `pause`/`unpause` sent a statement the server rejects;
  use the 0.2.0 clients ([#625](https://github.com/orlyatomics/orly/issues/625)).

The on-disk format is unchanged: a 0.1.x store opens under 0.2.0, subject to the open check above.

### Added
- **Added**: an optional shared secret for client connections and replication. Start `orlyi` with `--auth_token_file=<path>` (or `ORLY_AUTH_TOKEN_FILE`, or the token itself in `ORLY_AUTH_TOKEN`; `--auth_token=<value>` works but shows in process listings until `orlyi` scrubs it) and every connection must present the token before any statement runs. Over WebSocket the first message is `{"auth": "<token>"}`; over the binary protocol a new `TAuth` request (kind `'A'`) precedes the session request. A missing or wrong token is refused with `"status": "unauthorized"` (WebSocket, then close code 1008) or a refusal reply and hang-up (binary), raised as `UnauthorizedError` (TS), `orly.Unauthorized` (Python) and `ErrUnauthorized` (Go). Health checks need no token. A slave must present the replication token (`--replication_token_file`, `ORLY_REPLICATION_TOKEN_FILE`, `ORLY_REPLICATION_TOKEN`; by default the client token) to join a master; a mismatch is refused and logged on both sides, and the master keeps listening. Tokens are 16 to 1024 printable ASCII characters, compared in constant time and never logged. The TS, Python and Go clients take a `token` option and read `ORLY_AUTH_TOKEN_FILE` or `ORLY_AUTH_TOKEN` (TS in Node only); the MCP server and `orly_client` read the same variables, and the REPL also takes `--token-file`. Off by default: with no token the wire bytes are unchanged. **Operators enabling it must give the token to every client and every replica:** clients and slaves that have it keep working against a server without one, so roll it out to them first, then restart slaves and finally the master with the token; anything without it is refused from then on. `docs/PROTOCOL.md` has the protocol, the rollout order and a TLS-via-Caddy recipe for both the WebSocket and the binary port ([#710](https://github.com/orlyatomics/orly/issues/710)).
- **Added**: a "Security" section in the README and a trust model in `docs/PROTOCOL.md`: no authentication, run on a trusted network or behind an application that authenticates users, keep replication peers on a private network, and what `compile` over WebSocket allows ([#705](https://github.com/orlyatomics/orly/issues/705)).
- **Added**: the reporting port shows the global POV's layer count, `Global Layers = disk N; memory M`. Each disk file is one more place a read looks. Measured on x86 runners, a quiet single-key read took 0.3 ms against 2 to 4 files and 0.6 to 0.7 ms against about 300, roughly 1 µs per file. The disk merges keep the count down, so a count that stays high means they are behind. A new harness, `clients/smoke/run-layer-count.sh`, drives sustained writes of new keys with one concurrent reader, samples the count, and prints read latency, both during the writes and after them, as `METRIC` lines for ab-bench. With the default 8 disk merge threads, the count stayed at 2 to 5 files at 15,000 to 27,000 new keys a second. No write slowdown was added; #701 has the measurements behind that (#701).
- **Added**: a per-read budget. A method call that walks more rows (`--read_budget_rows`), or builds more result memory (`--read_budget_mb`), than it allows is stopped and refused with its own status, `"status": "read_too_large"` (over the binary protocol, an error starting `read too large`), instead of running until `orlyi` runs out of memory. Like `write_too_large` it is not retryable as sent. The defaults come from the memory budget: a sixteenth of it, at least 16 MiB, and one row per 256 bytes of that. `--read_budget_mb=0` turns the budget off. The TS, Python and Go clients raise `ReadTooLargeError`, `orly.ReadTooLarge` and `ErrReadTooLarge` for it; `docs/PROTOCOL.md` explains it ([#694](https://github.com/orlyatomics/orly/issues/694)).
- **Added**: a reopened disk store is checked for consistency at open, in every build ([#700](https://github.com/orlyatomics/orly/issues/700)). Every block the volumes hold must belong to exactly one owner (the system block, a base image, the append log, or a data or durable file in the file map), and each repo's data files must cover disjoint sequence ranges. Leaked blocks (#620's class) and overlapping or inverted ranges are logged at `LOG_ERR`; a block a live file owns that is free or waiting for discard (#610's class), or a block owned twice, refuses the open, because the next file allocated could be written over live data. `--open_check=false` skips the check, for recovering such a store. Reloading a repo now also logs each merge leftover it drops, and checks in release builds that what remains is strictly monotone (until now a debug-only assert). One summary line (`open check: N files, ...`) is logged at `LOG_INFO` on a clean store; the check reads each file's block list once and scans the block map once.
- **Added**: a fault-injecting test device and a harness that uses it (#608). `Sim::TFaultDevice` (test-only, `orly/indy/disk/sim/fault_device.h`) can fail the Nth read, write or sync the way a real device does, or lose power at the Nth sync: writes since a device's last completed sync are lost, or optionally torn at sector granularity. `Sim::TFaultEngine` runs the real file service on these devices, so a new engine can be opened over the image a power loss leaves. `orly/indy/fault_injection.test` loops N over a memory merge, a disk merge on both the plain and the fold path, a durable save with the durable merge, and a file-service base image. Each run happens in a child process, so an `abort()` or a hang ends only that run. A run must finish without hanging or leaking blocks, and after a power loss the engine must reopen with every acknowledged write intact. It found #618 (fold-path merge overlaps its input after a crash), #619 (durable files are not synced before they enter the file map), #620 (reload leaks the blocks of leftover merge inputs) and #621 (an fsync error kills the file service and hangs every later file-map change). All four are pinned as expected failures until they are fixed.
- **Added**: an `ab-bench` workflow (manual dispatch) for comparing two commits' performance on the same runner. Each shot builds release `orlyi` and `orlyc` at both refs, then `tools/maint/ab_bench.py` runs one command against each build, alternating AB, BA, ... for several rounds. It reports each metric's median per arm and the median of the per-round B/A ratios. The command and its harness come from the dispatching ref, so both arms run the same workload. Commands report numbers as `METRIC <name> <value>` lines, and the pool-pressure smoke now prints writes per second and the peak Update pool for each phase. This replaces the throwaway probe branches used for #584 and #587. Comparing runs from different machines once made #587 look 14% slower when it wasn't.
- **Added**: CI now runs the disk-full smoke a second time with write admission turned off (`ADMISSION=off clients/smoke/run-disk-full.sh`, which passes `--disk_reserve_mb=0 --disk_reserve_pct=0`), and requires that run to *fail* once its writers have started. If the smoke ever passes without admission, CI goes red, so a change that leaves it unable to notice missing admission can't slip through. Disk pruning (#592) is the obvious way that could happen: if overwrites stopped filling the disk, nothing would get refused.
- **Added**: `--prune_merge_history` (default on) turns off the global POV's merge-time pruning without touching `--allow_tailing`. Before this, the only way to keep every version on disk was `--allow_tailing=false`, which also disabled the `tail` statement. `--allow_tailing` now gates only `tail`. Each tail merge also logs, at info level, how many of its input updates it kept. New tests cover tombstones, `+=` written after a tombstone, updates that span two indexes, `+=` chains that span merge inputs or have their base outside the merge, and slave joins over pruned files with and without file sync (#592).
- **Added**: a batch can now mix methods. `try {pov} [pkg1 m1 <{...}>, pkg2 m2 <{...}>, ...];` runs calls to different packages and methods as one transaction, so several different writes (creating an entity and linking it, say) land together or not at all. It follows the same-method batch from #253: one commit, all-or-nothing (a call to an unknown package or method rejects the whole batch), and every call reads the same pre-batch snapshot. The reply is a JSON array with one result per call, and the entries may differ in type. The TS, Python and Go clients have `callMany`, `call_many` and `CallMany`. Both kinds of batch now run through one server path, and the same-method batch's reply and meta record are unchanged. A new CI smoke, `clients/smoke/run-multi-batch.sh`, covers mixed results, the all-or-nothing rule, snapshot reads and the same-method batch (#255).
- **Added**: the docker workflow now checks that the server *survives* writes, not just that writes answer. After the MCP smoke, it writes through all four POV flavours (five fresh POVs each) against the running container, waits, and asserts the container is still running with exit 0. The `v0.1.0` arm64 image passed every existing smoke while segfaulting just after the first write (#578). Run locally against the published images, the new step fails on `v0.1.0` arm64 (exit 139) and passes on `v0.1.1`.

### Changed
- **Changed**: an `insufficient_memory` refusal now says what memory admission compared (#719): the pool that refused, its blocks in use, the blocks promised to other writes in flight, the blocks claimed for merge and Tetris copies, this write's blocks, and the limit writers may use. The same counts go to the log line that records the switch to refusing. The message used to give only the blocks in use, so a refusal at 55% of the Update Entry pool looked like a bug when it was in-use plus claims past the 75% line.
- **Changed**: on a bare host, `orlyi` now binds its client (`--port_number`, 19380), WebSocket (`--ws_port_number`, 8082) and reporting (`--reporting_port_number`, 19388) listeners to `127.0.0.1` instead of every interface, because Orly has no authentication. **Operators must act:** a server whose clients, balancer or monitoring connect from another machine must now be started with `--bind_address=0.0.0.0` (or one interface's address, IPv4 or IPv6) or those connections are refused. Clients on the same host are unaffected. The replication listener (`--slave_port_number`) still binds every interface by default, so master/slave pairs across hosts keep working; the new `--slave_bind_address` restricts it to a private network's address. `orlyi --log_info` logs each bound address at startup (`client listener bound to 127.0.0.1:19380`). The Docker image passes `--bind_address=0.0.0.0` inside the container, so `docker run -p` keeps working; the docs now publish with `-p 127.0.0.1:8082:8082`, and say what `-p 8082:8082` exposes. The test balancer takes `--bind_address` too, also loopback by default ([#705](https://github.com/orlyatomics/orly/issues/705)).
- **Changed**: the `compile` statement over WebSocket, which builds the source it is sent with the server's C++ compiler for `install` to load into the server, is refused unless `orlyi` is started with `--allow_remote_compile`, on a bare host and in the image alike. The refusal is its own status, `"status": "remote_compile_disabled"`, raised as `RemoteCompileDisabledError` (TS), `orly.RemoteCompileDisabled` (Python) and `ErrRemoteCompileDisabled` (Go). No client or example in the repo sent `compile`; they compile with `orlyc` and `install`, which is unchanged. A server that relied on remote compile must add `--allow_remote_compile` ([#705](https://github.com/orlyatomics/orly/issues/705)).
- **Changed**: a single write too large ever to be merged, one with more entries than half the Update Entry pool's merge reserve, is now refused with its own status, `"status": "write_too_large"` (over the binary protocol, an error starting `write too large`), instead of a generic `"exception"`. Unlike `insufficient_memory` it is not retryable: split the batch. The TS, Python and Go clients raise `WriteTooLargeError`, `orly.WriteTooLarge` and `ErrWriteTooLarge` for it. The limit is `--update_entry_pool_size` × `--memory_reserve_pct` / 100 / 2, and shrinks with the memory budget; `docs/PROTOCOL.md` explains it ([#687](https://github.com/orlyatomics/orly/issues/687)).
- **Changed**: the fault-injection harness's fold-merge crash test now requires the reopen to free every block, so the leak #620 fixed can't come back unnoticed (#620).

### Fixed
- **Fixed**: a POV's writer backlog no longer overshoots its cap (#721). The writer backpressure caps each POV's unpromoted backlog at 1/32 of the Update pool in updates and of the Update Entry pool in entries (#584, #628), because a memory merge claims a whole copy of it (#629). It checked the cap only after a write had committed, so every writer that came in while the backlog was under the cap landed, and a writer whose backlog had not shrunk for 5 s then wrote anyway. In the batch-backlog smoke (8 writers of 200-write batches, cap 1,250 entries) the backlog peaked at 2,000 entries in every local run, and 42-72% of commits left it over the cap; on loaded CI runners it reached 3,000-5,600, and that merge claim got other writers refused. A write now takes its room in the backlog before it commits, counted with the room other writers hold under the repo's data lock, and waits there, before memory admission, while the backlog drains. A writer whose backlog has not shrunk for 5 s is refused with `insufficient_memory`, which clients retry, instead of writing past the cap. A write bigger than the entry cap gets room once the backlog is empty, and smaller writes wait behind it. With the fix the backlog peaked at 1,200 entries in every run, quiet, CPU-loaded, and on a 4-core topology. The reporting port has a new `Writer Backlog` line (peak entries and updates against the caps, and the stalled-backlog refusals), and the batch-backlog smoke fails if the peak passes the cap.
- **Fixed**: a writer waiting out write back-pressure no longer pins memory the merges are trying to free (#722). Its `TContext` kept a view of its POV and of every ancestor (the global POV, for a shared one) for the whole wait, and each view pins that repo's mapping and memtable as of the call, so the memory layers a merge had replaced since stayed allocated until the wait ended. `Try` and the batched writes now drop the context's views once the statement has read and committed, before the wait (`TContext::ReleaseViews`). Every read the statement makes, in the call and in resolving its effects, still comes from the one snapshot, and the result is already copied out; a read through a released context throws instead of seeing an empty repo, and a context with a key cursor still open refuses to release.
- **Fixed**: the batch-backlog smoke (`clients/smoke/run-batch-backlog.sh`, #628) failed intermittently on loaded CI runners, twice on `master`'s release job and once on a PR dispatch (#719). It treated a single refused batch, or a polled Entry pool peak at half the pool, as a failure, but how full the pools get swings with the runner's load: one failure had a batch refused at 76% in use, another polled a 20,051 / 40,000 peak with nothing refused. A refused batch is now retried after 50 ms, as the client contract says, and the smoke fails only when more than 1% of batches are refused, or when the polled Entry pool peak reaches 60%. A new CI negative control runs the smoke with the backlog cap off (`--tetris_backpressure_threshold=0`), where about a quarter of the batches are refused and the peak reaches about 75%, and requires it to fail.
- **Fixed**: `orlyi` now runs under ThreadSanitizer in CI, and the races and lock-order inversions that first run found are fixed. A memory layer's "taken" flag was a plain `bool` that merges set while views and mappings read it on other threads. It is now atomic, and only the release that drops the last reference reads it. That release was always ordered after the merge, so no layer leaked; a new `repo.test` case drives the race and checks that every merged layer is freed. A session added a POV by copying its durable pointer under the session's POV lock, while closing a session takes that lock under the durable manager's lock. The copy now happens outside the lock, and `Durable::TPtr`'s moves are `noexcept`, so a growing POV list no longer copies pointers under it. The reporting port read the durable pools' block counts and each volume's used-block count without the writers' locks; those reads are now atomic or locked. The TSan job builds `orlyi` and `orlyc` and runs the memory-drain smoke against them (`clients/smoke/run-tsan-server.sh`), with a negative control. It also found an inversion between a child repo's data lock and the Tetris player's mutex, which #660 removed; its temporary suppression is gone, so `orly/tsan.supp` is empty again (#713, #717).
- **Fixed**: unpausing many POVs whose backlogs had filled the update pools left the pools full for good (#660). Each Tetris round copied out every waiting child's update before promoting one, so with 32 such POVs the copies took everything memory admission had kept free, the claim for the one promotion was refused, and the round was dropped and started again, forever. A round now takes every waiting child's promotion hold as before, but copies a child's update only when its turn comes, oldest first, so it holds at most the copy it is about to promote. No copy is made under the player's lock any more. The commutative fast lane, which must read every child's update to sort them, still copies them all. The memory-full smoke now also drains 32 paused POVs filled by 32 writers.
- **Fixed**: a disk merge always took the leftmost eligible pair of files, so when that pair couldn't fit in the free space, the merge wrote until it hit the data floor, failed, and retried the same pair every few seconds forever. A smaller pair behind it that would have fit was never tried, and the failed attempt's claim kept write admission's threshold at the big pair's size. The merge now skips a pair whose inputs are larger than the room above the data floor that other merges haven't claimed, and takes the leftmost pair that fits. When none fits it writes nothing and looks again after a backoff, without holding writes off for a merge it never started (#692).
- **Fixed**: collecting with `reduce` (`[..] reduce (start empty [int]) + [that]`, or `| {that}` into a set) now takes time linear in the number of elements, not quadratic. The generated reduce function took its carry by `const&`, so `start + [that]` copied the whole carry on every step: N(N+3)/2 element copies for N elements, 501,500 at N = 1,000 and 32,012,000 at 8,000. When the body's one `start` runs once per call, which is whenever it isn't inside a nested filter, sort, inner reduce or the like, orlyc now takes the carry by value and emits `std::move(carry)` at that use. `Rt::Reduce` gains an overload that moves the carry into each step, and list `+`, set `|` and `-`, and dict `+` and `-` gain versions that update an expiring left side in place. Collecting is now 2 element copies per element: 2,000 at N = 1,000 and 16,000 at 8,000. `collated_by` still copies its carry (#697).
- **Fixed**: a memory merge that had written its file but found no pool room to publish it slept on the merge runner until room appeared. Every repo's memory merge runs on that runner, and another repo's merge is often what frees the room, so the wait could last until shutdown, with no repo's memory merging meanwhile. The merge now keeps its layers taken, re-queues itself with the same backoff, and finishes the publish at the start of its next turn, so the runner moves on to other repos (#691).
- **Fixed**: reading a hot `+=` key no longer costs time quadratic in its unmerged writes. The read folds every unmerged entry on the key, and drops a second copy of any update it has already folded by its UpdateId. It did that by scanning a vector of every id it had seen, so a key with W unmerged entries took W(W-1)/2 comparisons to read. The ids now go in a hash set. In `context_fold.test`, a read of a key with 500 unmerged `+= 1`s went from 124,750 comparisons to 500 hashes, and with 4,000 from 7,998,000 to 4,000. `TContext::GetFoldDedupProbes()` reports the count (#696).
- **Fixed**: `take N` no longer steps its source onto element N+1. After the Nth element it advanced the source once more and then tested it before checking the count, so a `take` over a key cursor decoded, and could fetch a page for, an element it then threw away. It now checks the count first and stops stepping once it has N (#699).
- **Fixed**: `sorted_by` now keeps ties in their input order, and a comparator like `lhs <= rhs` can no longer crash it. It used `std::sort`, which leaves the order of equal elements unspecified, so results could differ between builds. With a comparator that isn't a strict ordering, `std::sort` is undefined behaviour: sorting 1,000 equal values with `<=` read past the end of the vector under AddressSanitizer, and segfaulted in a debug build. It now uses `std::stable_sort`. A comparator that holds for an element against itself (`<=`, `>=`, or one that is always true) is sorted by its strict part instead, so `<=` gives exactly the order `<` does; that check costs one call per sort, and the strict part a second call per comparison only for such comparators (#698).
- **Fixed**: `Rt::BidirShortestPath` no longer walks a hub's whole connected component looking for a target it can't reach. Past depth 2 it grew only the source's side, kept a full path for every node on it, and had no limit, so a query from a hub to a disconnected target read every edge reachable from the hub. It now always expands the smaller of the two sides, keeps one parent edge per node and rebuilds paths at the end, and stops at a depth limit (default 16 edges) or a node limit (default 100,000 nodes visited). It returns a `TShortestPathResult` whose status says whether it found paths, proved there are none, or hit a limit; the limits are an optional last argument. The search itself moved to `orly/rt/bidir_bfs.h`, where a new test runs it on in-memory graphs. On a hub with 1,000 spokes of 20 leaves each and a target in a separate three-node component, the old search read 42,002 edges from any starting node; the new one reads 1,006 from the hub and 27 or 28 from a spoke or a leaf, and none at all when the target has no edges. No orlyscript builtin calls it yet, so no program changes (#695).
- **Fixed**: a pov made before a slave joined couldn't be used after a failover. Its durable record reached a slave only if the pov was saved again while the two were paired, because the join sent the master's live repos but not the povs' records, so the promoted slave refused the pov (`durable object doesn't exist`) although it had its repo. The join now sends the saved record of each pov whose repo it inventories, in batches of at most 1024 records or 1 MiB, before the slave syncs. They travel as durable saves on the live stream's existing message, so a slave from before this change stores them too. Sessions still reach a slave only when saved while paired; reads through a pov don't need them. Covered by `import_replication.test`'s new `JoinSendsPovRecords`.
- **Fixed**: a slave could lose the record of a pov (or session) the master saved while they were paired, so after a failover that pov failed with `durable object doesn't exist`. The master sent each durable save's ttl as a bare seconds count, which the slave did not read back as the ttl sent (a unit test read back 281474219468880 for 600). The slave then stored the record with a garbage deadline, and its durable layer dropped it as expired at the next write or merge whenever that deadline wrapped below the current time. Which records were lost varied from run to run, which made `import_replication.test`'s `SlaveInventoryKeepsPovShape` (#676) fail intermittently on master in debug and release builds. The ttl now travels as a Sabot duration, as a repo's ttl already did, and the slave decodes durable saves through one function, `TReplicationStreamer::ForEachDurable`, which the new `orly/indy/replication.test` checks against the encoder.

Every page is still read from disk once, so the total I/O is unchanged. More of it is now prefetched: reading one 16-page block sequentially, synchronous page reads drop from 8 to 5 (#594).
- **Fixed**: a vectored read whose submit fails part way no longer hangs the reader. Such a read, like a page cache prefetch on a striped volume, is sent as a group of I/Os that reports once, when all of them have completed. If one submit threw, for example because no disk event could be allocated, that I/O and the ones after it never completed. The group never reported, and the trigger its caller waits on stayed one completion short forever. The failed submit now delivers an error completion for each I/O that wasn't submitted, so the group reports once, with the error. The group's error and completion count are now updated together under a lock. Before, a completion still recording an error could have it missed by the last one, and then write it into a group that had already been freed (#594).
- **Fixed**: the ThreadSanitizer CI gate could not fail on a broken test. Each test ran with `|| true`, and only `WARNING: ThreadSanitizer` lines in the logs were counted, so a test whose EXPECTs failed, that crashed at startup, or that hit the 600 s deadlock guard still passed. A non-zero exit now fails the job. The job also runs a negative control first: `base/tsan_control.test` races two threads on a plain int, and TSan must report it. If that race goes unreported, the instrumentation or the suppressions would hide every other race, so the job fails. The curated set gains the lock-free `base/inv_con/atomic_{ordered,unordered}_list` tests, `base/latch`, `orly/indy/repo` (where #592's pruning merges live) and `orly/indy/transaction_base`. Making the gate able to fail showed that `orly/indy/fiber/fiber_lock.test` has hit the 600 s timeout under TSan on every master run (#613). It is listed as a known timeout: reported as a warning, with a second warning if it starts passing.
- **Fixed**: a safe repo's disk use no longer grows with every write ever made. Its disk merges kept every version of every key, and every update-index entry, forever, so overwriting the same keys eventually filled the disk and left the server refusing writes (#590). The global POV's disk merges now drop superseded versions, using the existing tail-merge pass behind the `tail` statement. Each merge keeps every key's current version, and keeps whole any update that still holds one. Nothing else reads that history: a slave join walks a view that pins the files it started from, live replication ships transactions rather than files, and child POVs, whose updates Tetris still has to promote, are never pruned. The tail pass used to drop a `+=` key's earlier increments and its base, so after a `tail` the key could read back as its last increment alone. It now keeps that history. A merge output also records the whole sequence range of its inputs, so a merge input that a crash leaves behind is still recognised and dropped on reload. `--prune_merge_history=false` turns the pruning off. Measured on native arm64 with 8 writers overwriting 100k keys on one safe shared POV for 15 minutes, with the image's default volumes. On master, the low point between discard passes climbed from 35 to about 150 MB, writes started being refused for space at about 480k, and 723 were refused in all; usage settled at 143 MB after 700k writes. With the fix, the low point stayed between 45 and 75 MB, no write was refused, and usage settled at 44 MB after 752k writes (#592).
- **Fixed**: WebSocket sessions no longer collect a notification for every write. Each write promoted out of a shared POV queues an `Accepted` notification on the writer's session, and with a slave attached each replicated write queues a `Replicated` one too. Only the binary protocol ever delivers and removes them, so a WebSocket session kept every one it was given, in memory and in each save of the session to the durable store. A session now stops queuing notifications while a WebSocket client holds it, and starts again when a binary client attaches, so a binary client that reconnects still gets what arrived while it was away. Measured on native arm64 with 8 WebSocket writers on a safe shared POV: the durable store settled at 4.6, 8.2 and 12.9 MB after 100k, 200k and 300k writes before the fix, and stays at one 64 KiB block after it (#591).
- **Fixed**: a page prefetch whose read fails no longer hangs the reader. The page cache's two async loaders registered each read on the stream's completion trigger but completed it only on success. So when a read failed, the fiber destroying the stream waited forever. The multi-page loader also left a failed page looking as if it was still loading, so any later read of it spun forever instead of failing. Both loaders now complete the trigger on failure, and both mark a failed page as loaded with an error, so a read of it throws. A stream's destructor no longer throws when one of its prefetches failed, which would have terminated the process. It logs the failure instead, because a reader of that page gets the error from the page itself. Nothing hit this in a test or a run: the cache's reads abort on a checksum failure before reporting it, so only a device I/O error or a failed submit reaches this path (#596).
- **Fixed**: `orlyi` and `orlyc` now shut down gracefully on SIGTERM, as they already did on SIGINT. `RunUntilCtrlC` blocked every signal and waited with only SIGINT unblocked, so a SIGTERM stayed pending forever. `docker stop`, Kubernetes and systemd all send SIGTERM, and they then waited out their timeout and SIGKILLed the server, so the flush of dirty memory layers (#440), the durable writer's final drain (#277) and the client drain (#460) never ran. The image `exec`s `orlyi`, so this hit every container. `tests/restart_test.sh` now stops the server with SIGTERM on its first cycle and fails unless every shutdown completes on its own, where before it fell back to `kill -9` silently (#598).
- **Fixed**: `orlyi` no longer aborts when its disk fills. It refuses writes instead, and keeps serving reads. Writes are refused, with `"status": "insufficient_storage"` over WebSocket or an error starting `insufficient storage` over the binary protocol, while free plus discard-pending space is below a reserve plus the inputs of running disk merges (and of one that failed for space in the last minute, so its retry has room). The reserve is `--disk_reserve_mb` if set, else `--disk_reserve_pct` of the disk (default 10%, never less than the smaller of 64 MiB and a quarter of the disk). Reads, new sessions, new POVs and pause/unpause are never refused. Writes are accepted again on their own once space is back. Below half the reserve, flushes and data merges stop too, so the rest stays for the durable store (sessions, POVs) and the file map. The durable writer and merger, and the file map's base image, no longer abort on a full disk. The writer keeps a layer it can't write readable in memory, releases its savers and retries. The merger hands its inputs back and backs off. The base image keeps spare blocks, and if it must grow with nothing free, it waits instead of aborting. Durable files free their blocks if they fail before reaching the file map. The block map is now sized in whole words. Before this, a volume whose block count wasn't a multiple of 64 could never allocate its last few blocks, though they counted as free. The allocator's out-of-space log lines are rate-limited, and the reporting port gains a `Write Admission` line. The TS, Python and Go clients raise a dedicated error for the refusal (`InsufficientStorageError`, `InsufficientStorage`, `ErrInsufficientStorage`). Measured on native arm64 with image defaults (256 MB / 64 MB), 8 writers overwriting 100k keys: step 3 stalled at ~1.35M writes and then aborted in the durable writer. Now writes are first refused at 464,719 writes, with no out-of-disk error and no abort; after 5 minutes idle, a read and a write both worked. With the writers retrying through refusals for 20 minutes, 728,621 writes went through and 1,338 were refused. A concurrent reader made 5,631 reads with none failing, the slowest taking 33 ms. Nothing aborted, and the server shut down cleanly (#590).
- **Fixed**: a merge that runs out of disk space no longer aborts `orlyi`. It hands its inputs back and retries after a backoff (100 ms, doubling to 3.2 s). A disk merge unmarks the two layers it took, and a memory merge puts back the layers it was flushing. Both re-queue themselves, and the merge queues are ordered by due time, so a repo that is backing off delays no other repo. Three things had to change for the retry to be safe. A failed memory-layer flush used to report every update in it as permanently failed, which freed the transactions' completion records that the retry later completes. It now leaves those reports pending. The fold step's intermediate file, left in the file map with no owner when the fold failed, is now removed. A tail that runs out of space hands its layer back and logs, instead of aborting. Writes are not refused yet when space runs low, so while the disk stays full they collect in memory until the update pool's backpressure slows them down. The durable writer and merger still abort on a full disk. The retry lines in the log are rate-limited to one every 10 s (#590).
- **Fixed**: an I/O completion trigger destroyed by an exception now waits for the reads and writes it is still tracking. `~TCompletionTrigger` was empty, so a throw between submitting I/O and calling `Wait()` (a `TDiskFull` from a sorter spill in the middle of a merge, say) freed a stack-owned trigger that in-flight completions then called into. Today such a throw ends in `abort()`, so nothing reaches the dangling trigger; the merge retry that #590 needs would. The submit paths now always deliver a completion they have registered, even when the submit itself throws, so the wait can't hang. Each fiber also keeps its own C++ exception state across switches now. A fiber that parks mid-unwind (as this wait does, and as the index-file destructors from #593 already did on real disks) used to leak its in-flight exception to every other fiber on its runner. There, `std::uncaught_exceptions()` read one too high, and the index-file destructors rely on it to tell an abandoned build from a finished one (#590).
- **Fixed**: a full volume no longer aborts `orlyi` while another volume still has room. `TStrategy::TryReserveSeqBlocks` called `abort()` when its volume ran out, so `TVolumeManager`'s fallback to another volume never ran. With the image defaults (256 MB fast, 64 MB slow), a safe repo's disk merge filled the slow volume and killed the server while the fast one still had free blocks. The allocator now throws a typed `TDiskFull`, the fallback works (logged once), and `TDiskFull` reaches callers only once every volume is full. File builders now release what they reserved when they unwind. `AppendReserveBlocks` frees whatever the failing call took. `TDataFile`, the merge and the sorters' spill files free their blocks unless the file has already gone to the file map. The index-file destructors no longer write their metadata into blocks that may never have been reserved. Running out of space on *every* volume still aborts, now with a log line naming the merge or loop that hit it: merges, the durable writer and merger, and the file service can't wait for space yet. Measured on native arm64 by overwriting 100k keys in a loop: master aborted at ~431k writes with the slow volume full. With the fix, the slow volume filled at ~530k writes and the server carried on. It aborted at ~761k writes, when no volume had room for a disk merge, whose inputs stay allocated until it finishes (#590).
- **Fixed**: `Util::SleepUntil` never slept. Its comparison was inverted, so it slept only for deadlines already in the past, and since 2014 every interval passed through it has been a no-op. It now sleeps until the deadline, and that matters for three kinds of caller. **The merge-mem and merge-disk loops** still honoured each repo's next-merge deadline (#227), so the broken sleep made them busy-wait for up to 40ms after every merge step. Measured on native arm64 release builds with writes under way, the fix cuts `orlyi`'s CPU by 65–85%, with throughput within run-to-run noise. With one writer, the old build used 10.5–15.5 CPU-seconds per 20s and the fix 1.8–4.6; with eight, 11.6–12.3 against 4.9–5.0 per 15s. **The replication loop and the durable writer and merger** never actually waited out `--replication_interval`, `--durable_write_interval` or `--durable_merge_interval`, and still don't. Their dead sleeps are removed, so turning a real delay on is a measured decision of its own. A working 100ms replication interval, for example, would hold every write back from merging for up to that long, because the loop gates `ReleaseUpdate` even in SOLO. The flags are still accepted. `orly/perf/kv_exercise` now paces its inserts at `FlushIntervalMs`, as it always intended (#576).
- **Fixed**: concurrent writers no longer exhaust the Update pool and abort `orlyi`. Eight writers on one shared POV used to kill the server within seconds whenever the pool was small, and the pool is sized from the host's free RAM at startup. The root cause was the repo layer cleaner wedging. To free a dead disk layer it visits every runner to drop that file's caches, and the Tetris player's runner never let it back on: the player looped `Play(); usleep(0);` without yielding, and a runner only takes in frames handed over from other runners once its own queue goes idle. From then on nothing was ever freed. Every child merge copied the unpromoted backlog into a new layer while the old copy stayed allocated, so occupancy grew with the square of the write count and kept climbing after the writes stopped. Once the pool filled, `StepMergeMem` called `abort()`. Five changes. The player yields with `YieldSlow()` each round. The cleaner frees cheap memory layers first and visits the runners once per batch of disk layers rather than once per layer (~24ms each, which had fallen behind the merges). Write backpressure caps each POV's backlog at 1/32 of the Update pool and also waits, bounded at 5s, while the Update or Update Entry pool is more than half full. A merge that runs out of pool space before it publishes anything rolls back and retries instead of aborting. A Tetris round that hits `bad_alloc` is retried instead of silently killing the player. A new CI smoke (`clients/smoke/run-pool-pressure.sh`) runs 8 writers, on one shared POV and then on a POV each, against a 20000-update pool on the release build. Before the fix it aborts within about 2,000 writes; after it, both phases run 30s with no errors, and the pool drains once the writes stop. The single-POV, 8-writer throughput on a 100k pool is about 15–20% lower than with an uncapped backlog, and single-writer throughput is unchanged (#584).

## [v0.1.0] — 2026-09-17

First numbered release. Everything below had already shipped to `master`; this draws a line under it so
there is an immutable image and a version string to refer to, rather than only a moving `:latest` and a
commit hash. The version matches the clients already published at `0.1.0` — `@orlyatomics/orly`,
`orly-mcp`, `orly-repl` on npm, and the `clients/go/v0.1.0` module tag.

### Fixed
- **Fixed**: `orlyc` no longer hangs on aarch64 while tearing down its embedded test server. A fiber's stack outlives the OS thread that last ran it — frames come from a cross-thread pool and are routinely re-latched onto a runner on a different thread — but GCC computes the thread pointer once per function (one hoisted `mrs x, tpidr_el0` on aarch64) and derives every `__thread` access from it, so `TFrame::Run()`'s read of `TRunner::LocalRunner` *after* the runnable returned yielded the previous thread's runner and `longjmp`ed onto that thread's scheduler stack. Two OS threads then executed one stack, the hijacked runner's `Run()` never returned, and `~TDurableManager` waited forever on `SchedulerExitedSem` inside `TServer::Shutdown()`. The three fiber thread-locals are now `TFiberSafeLocal` slots read through `noipa` accessors, so the thread pointer is re-read at every access; nothing cheaper works (`volatile`, `thread_local`, an `asm` memory clobber, `returns_twice`, and all four `-ftls-model` settings all still emit one loop-invariant `mrs`). x86-64 folds the TLS base into each access's addressing mode, which is why only arm ever showed it (#554).
- **Fixed**: `durable_manager.test`'s `SemFiresOnlyAfterFlush` no longer fails intermittently on loaded CI runners. It asserted that the durability sem has *not* fired immediately after `Save()` — sound only while less than the manager's write delay has actually elapsed, and at a 300ms delay a descheduled test thread could legitimately miss the window, so correct behaviour reported as a failure. The negative assertion is now guarded on measured elapsed time and the fixture runs at a 2s write delay, so the skip should be vanishingly rare and, when it happens, means "unprovable here" rather than "regression". The #277 property it guards is unchanged and still caught: a synchronous `Save()` push fires the sem at elapsed ≈ 0, inside the window, and fails the assertion (#551).
- **Changed**: the docker workflow builds the image on both `linux/amd64` and `linux/arm64` and, on a publish, stitches them into one multi-arch manifest — so `docker run ghcr.io/orlyatomics/orly` resolves natively on Apple Silicon instead of printing a platform-mismatch warning on the first command in the README. The side benefit is that every existing gate — MCP smoke against the containerised server, in-container `orlyc` compile, REPL entrypoint mode — now runs **on the arm image too**, so the published arm64 artifact is proven to work rather than merely to build. The manifest job runs only when both legs pass, and asserts the published manifest advertises both platforms rather than assuming the stitch worked (#548).
- **Changed**: the docker image job reports `nproc` and `free -g` alongside the architecture, and takes its build parallelism and timeout from the matrix — 4 workers / 90 min on x86, 2 workers / 180 min on arm64. The first arm attempt was killed at the 90-minute cap still inside `jhm -c release`, while the same runner class completes `make debug` in 14 minutes (ci.yml). The difference is LTO, which is memory-hungry and largely serial at link time, so if the arm runner has less RAM per core then *fewer* concurrent LTO jobs is faster rather than slower. That is a hypothesis; the capacity report is what confirms or kills it, and not having it is why the first failure was uninformative (#548).

The help previously showed only assignment (`new <['k']> <- 1`) and read, so the one operation the project is pitched on was undiscoverable from the prompt: substituting `+=` into the documented write form fails with an internal compiler path (`orly/type/add_visitor.h, 50`) and the follow-up read returns `0`, which reads as a silently wrong write rather than a syntax error (#548).

The concurrent-writer problem and a copy-pasteable 30-second REPL demo (both operators, with their real output) come first; the MCP server is promoted from a parenthetical to a first-class quickstart with a working `npx -y orly-mcp` client config; the 2019-dormancy status paragraph moves from above the fold to its own `## Project status` section near the end. The Docker section now states that the published image is `linux/amd64` and runs under emulation on Apple Silicon rather than implying it is native on "any host" (#548).
- **Changed**: the disk cache and fiber scheduler now use `__builtin_prefetch` instead of `_mm_prefetch`/`<xmmintrin.h>`. Identical codegen on x86-64 — gcc lowers locality 3 and 2 to `prefetcht0`/`prefetcht1`, which is exactly what `_MM_HINT_T0`/`_MM_HINT_T1` emitted — but it also compiles on aarch64, where the SSE header does not exist. These were the only x86-specific constructs in the tree: there is no inline assembly anywhere, and the fiber fast path is `setjmp`/`longjmp` bootstrapped from `ucontext`, both POSIX, so there is no hand-rolled context switch to port. Verified with an explicit-instantiation probe, since every changed cache site lives inside `TCache<PageSize>` and `-fsyntax-only` on an includer does not compile class-template member bodies (#548).

It matters because the published docker image is amd64-only, so Apple Silicon users hit a platform-mismatch warning on the first command in the README (#548).

It was a 32-bit-x86-era leftover and a verified no-op on the only supported platform — `g++ -dM -E` emits a byte-identical macro set with and without it on x86-64, `__SSE2__` included — while being a hard `unrecognized command-line option` error on aarch64, which killed the bootstrap before a single translation unit compiled (#548).
- **Added**: aarch64 now builds clean and passes `make test` — 1753 build jobs and 203 test binaries, zero failures, on a native arm CI runner. The entire gap between "Linux only, x86-64" and a working arm build was two changes: `_mm_prefetch` → `__builtin_prefetch`, and dropping a `-msse2` that was a verified no-op on x86-64. No inline assembly exists anywhere in the tree and the fiber fast path is `setjmp`/`longjmp` over `ucontext`, both POSIX, so there was no context switch to port. `README.md` records this as "known to work, not yet released against" — the CI job stays informational rather than becoming a gate, because one green run is evidence and not a support commitment (#548).

The i/o thread now polls the destruction semaphore directly (and closes its pipe end on the way out, which also unblocks a dispatch thread parked mid-`Read()`), and the dispatch thread closes the pipe on its exception path too. - **The bulk-import / master-slave replication arc** (#367, #497, #498, #499, #500, #501, #503; one PR, pinned end-to-end by the new `orly/server/import_replication.test`, the first master/slave replication coverage anything in CI runs). Writing that test peeled seven stacked defects off the import+replication path, most of them 2014-vintage and latent because the destination block layout, not the code path, decided whether they fired:
  - **#367 — an index id minted by the bulk importer never replicated.** The importer's `SaveIndexNamespaceMapping` + `IndexIdSet` insert lacked the `TIndexIdReplication` enqueue the package-install site has, so a live slave never learned the mapping while ordinary writes to that index still replicated under the raw id — a promoted slave would bind the package to a divergent id and serve empty reads, or abort at startup on the unmapped data files. The duplicated registration logic is now one `TServer::RegisterAndReplicateIndexId` used by both sites (both `TODO(#367)` tags retired). With #498's solo-import rule the enqueue is belt-and-suspenders on the importer path today (a solo server discards its replication queue; joiners get the mapping from the join-time index-map walk, which the test asserts via the slave's "Replicating index" application log) — but the helper keeps install and import behaviorally identical if live import replication ever lands.
  - **#497 — a single-file import passed uninitialized sequence numbers to `AddFileToRepo`.** `ImportCoreVector`'s `final_saved_low/high/num_keys` were only assigned by the merge phase, and a one-file import skips every merge round: debug builds died on the `HighestSeq >= LowestSeq` assert in `TDiskLayer`, release builds silently registered a garbage sequence range. The load jobs now record each written file's `WriteFile` range and the no-merge path seeds the final range from it.
  - **#498 — an import on a replicating master desynchronized sequence numbers and killed the slave.** The importer writes data files and burns a 10M-per-file `UseSequenceNumbers` reservation entirely outside the replication stream, so a live slave died applying the next replicated write (`ensure_or_discard` assert), and even a slave joining *after* the import died in `SyncInventory` (the reservation left highest-materialized ≠ next-1). Imports are now what they factually are, a solo-server bootstrap operation: `BeginImport` refuses unless the server is solo, `WaitForSlave` holds an accepted join until a running import finishes (one gate covers both directions), and the import returns its reservation's unused tail (`TRepo::ReleaseUnusedSequenceNumbers`) so post-import joins sync a consistent range.
  - **#500 — a slave disconnect killed the master.** `WaitForSlave` never released the listener after its one accept was consumed, so the demote path's re-entry died re-binding the slave port (`EADDRINUSE` escaping a fiber is fatal). The listener is released once consumed, and the bind retries while a previous listener drains instead of killing the server. The test kills a slave outright and asserts the master demotes, stays up, and accepts a replacement slave.
  - **#499 — system-repo commits leaked onto the replication stream, with two distinct failure modes.** The system repo is node-local state: each server records its own repos, installed packages, and index-namespace mappings, and a slave rebuilds them from replication *control items* (`TRepoReplication`, `TIndexIdReplication`) — which is why `NewTransaction(false /* we replicate system changes seperately */)` already existed. But the three system-repo writers (`SaveRepo`, `SaveIndexNamespaceMapping`, `SaveInstalledPackage`) used the replicating default, so every install on a paired master (a) shipped a transaction against the slave's *independently numbered* system repo — the `ensure_or_discard` sequence assert killed the slave whenever its local numbering lagged the master's watermark (a coin-flip race), and (b) on the master, the notification pass decoded the commit's void metadata into a `Server::TMetaRecord` unguarded, threw, and silently skipped the batch's remaining client acks (`RunReplicateTransaction error: [not implemented]`). The three writers now pass `false` like the fourth always did, and the notification-pass decode is guarded like its sibling global-pov branch as defense in depth. The test installs a second package on the *paired* master, which also pins the live-stream side of #367: that package's index id must reach the slave via the `TIndexIdReplication` enqueue (the first package's mapping traveled with the join-time walk instead), the master's log must stay free of notification-pass errors, and a subsequent write's ack must still arrive.
  - **#503 — a server push racing `~TClient` aborted the host process.** `Rpc::TContext::Read` calls `shared_from_this()` when the peer sends a request, and the server pushes notification requests at its own cadence; one arriving while the client's shared count was already zero threw `std::bad_weak_ptr` into the dispatch thread's top-level catch, which `abort()`s — taking the whole embedding process with it (reproduced ~1-in-3 by the new test's connection churn). Destruction is now flagged before the service threads are signalled, and their top-level catches exit the thread instead of aborting when teardown is underway; a live client's exception still aborts as before.
  - **#501 — the data file delivered by join-time file sync was unreadable on the slave.** `TMetaRewriter` (which rewrites a synced file's header for the destination block layout) wrote the *block count* where the reader — and the original `TDataFile` writer — use the count of run-length `(block_id, num_blocks)` pairings. Whenever the destination blocks were contiguous (always, on a fresh volume or `--mem_sim`) the reader over-read the pairing list and parsed everything after it as garbage, most visibly the index-segment offsets — the slave's next file merge or read died on a `ByteOffset <= EndOfStream` assert. On 2014's fragmented volumes one-block-per-pairing was common enough for this to ship latent.

### Fixed
- **server: updates that never touch `now` no longer record run_time = 2013-10-23 in their meta record** (#494). All three commit paths in `session.cc` defaulted the `TMetaRecord` `run_time` with a hardcoded 2013 sentinel (the moment the line was first written) when `GetOptNow()` was unknown. Since `Rt::TContext::Now()` memoizes wall time on first use and the meta record is built after the method runs, the sentinel only landed when neither the client nor the executed method (nor a predicate) ever evaluated `now` — so assertion replay was never affected, but every time-agnostic update was durably recorded as having run on 2013-10-23 17:47:14. The shared `GetRunTime` helper now falls back to the commit-time wall clock, which replay cannot observe (a replayed predicate that reads `now` implies the original evaluated it, forcing the recorded-time path).
- **indy: the on-disk update index's per-sequence-number Metadata/Id cores survive writes and merges** (#323). Three defects in the same seq-index field pair, one of them the issue's original subject: (1) `TMergeDataFile` wrote default-constructed (zeroed) Metadata/Id cores for *every* merged sequence number — the `#if 0` block #323 tracked — so any update surviving an LSM compaction lost its meta record; the merge now streams each source file's update index, keeps the surviving sequence numbers' meta/id notes through the tail-merge keeper filter, remaps their cores into the merged main arena (via a new miss-tolerant `ResolveRemapTolerant` join), and the update-index writer consumes the result in sequence order. (2) `TDataFile` emplaced the cores into its update collector *without* remapping them from the update's in-memory suprena — whose "offsets" are raw note pointers — to the on-disk main arena, so any indirect metadata (every real session update carries a `TMetaRecord`) hit disk as a dangling pointer-valued offset; the notes were always copied into the main arena, only the core offsets were wrong. (3) Both writers seeded their write loop's meta/id from default-constructed cores and only reloaded on a sequence-number change, zeroing the first sequence number's fields even where the rest were right. Read side unchanged (`TUpdateWalkFile` — feeding Tetris's `GetLowestUpdate` promotion and master→slave replication, which is how the zeroed cores were reachable in production). Merging files written before this fix is tolerated: their dangling offsets resolve to nothing and are dropped with a syslog warning, matching their prior (unreadable) state. The four `TODO(#323)` `logic_error` stubs (`TMyMergeArena`/`TMergeIndexFile` `GetStartingBlock`/`ReadMeta`) are unreachable by design — those wrappers' streams locate blocks via `FindPageIdOfByte` — and now say so instead of claiming to be unimplemented. New `MetaIdRoundTrip` fixture pins meta/id round-trips through plain data files (including the first sequence number), a plain merge, and a tail merge that drops a history-only sequence number.
- **base/server: scheduler jobs are cancellable; every long-lived host job is cancel-or-joined at teardown** (#462, the #440/#463 arc's last structural follow-on). `TScheduler::Schedule` queues past the worker cap but never launches another worker, so a long-lived job that never got a worker could neither be joined (its started/exited handshake never ran) nor safely ignored (a worker freeing up mid-teardown would start it against dying state) — the teardown joins had to skip never-started loops and carry a documented residual hazard. New `ScheduleCancelable`/`Cancel`: the queue holds the closure through a shared handle, `Cancel` empties it under the scheduler lock, and a worker taking the job empties it the same way, so exactly one side wins and the owner gets an exact answer — `if (!Cancel(handle)) exited_latch.Pop()`. All the teardown-relevant owners convert: `TServer` (the runner-loop hosts, the BG fast runner, the accept loop — which previously had no join at all — and the housekeeper, whose started-flag skip is retired), `~TDurableManager` (which would previously deadlock outright if a host job starved: it popped fiber sems its writer/merger could never push), and `~TFileService`. `TScheduler::Shutdown` now drains the queue (nothing can start once shutdown begins) and its starved-jobs warning reports only live, never-cancelled leftovers — an owner contract violation, not noise. New scheduler.test fixtures pin cancel-before-take, cancel-after-take, and the refused-job null handle.
- **fiber/server: the #463 teardown race — cross-runner frame handoffs no longer live on the runners** (#463). - **code_gen: common subexpression elimination is live again, emitted in dependency order** (#297, #298). The per-scope interner has always deduplicated structurally-identical expression nodes, but the CSE hook it fires on a duplicate fetch (`TCodeScope::AddLocal`) was disabled with "sorting out dependency ordering issues": locals were emitted in arrival order, and when a larger expression is CSE'd before one of its own subexpressions is, the subexpression's `auto` definition would land *after* the local referencing it — use-before-def in the generated C++. `WriteStart` now emits locals in dependency order (stable Kahn over the `AppendDependsOn` edges restricted to the scope's own locals, insertion order as the tiebreak, hard error on the structurally-impossible cycle), which makes every dependency graph load-bearing — hence #298 in the same change: `TMatch`/`TSplit` were the only two of ~30 `AppendDependsOn` implementations inserting a child (`Regex`) without recursing into it (already a live, if narrow, bug via child-func definition ordering). Leaves whose emission is already a name or constant (literals, typed leaves, context vars, arg refs) are excluded from CSE. The `that` context (assert/effect subjects) now materializes on its second use, as a local of the scope that *owns* the context rather than whichever nested scope is active (an inline may only become a local of the scope it was built in, or an inner lambda would define a variable an outer scope references). Safety, verified: `if/else` arms build in their own `TInlineScope`s, so CSE cannot hoist a throwing subexpression past its guard; runtime sequences are cursor factories, so a shared generator is safely re-traversable. New interner tests pin the duplicate-fetch-creates-a-local behavior, the leaf exclusion, and def-before-use emission under inverted arrival order.
- **disk: `TCompletionTrigger`'s wake/destroy handshake closed — three defects in one rewrite** (#452, the residual instances of the #386/PR #449 free-on-wake class, found by inspection during that arc). The trigger is typically stack-owned and destroyed the moment `Wait()` returns, but `Callback()` bumped `NumFinished` and read `Result` *outside* the spinlock — a fast-path waiter could observe the full count, return, and free the trigger while the final completer was still walking into the (freed) lock to write `Result`. And once an error was recorded, the outer `switch (Result)` swallowed every later completion entirely — so an error landing *before* the waiter parked left the trailing successes unable to wake it at all: a hang, not just a race. New contract, all under the spinlock with the wake issued from stack copies after the unlock: the completion count alone decides the wake (the waiter runs only after every outstanding completion has arrived, error or not), `Result` is the sticky first failure and is thrown by `Wait()` at the barrier. - **Batched / pipelined writes** (#253). A batch `try` statement — `try {pov} pkg method [<{...args1}>, <{...args2}>, ...];` — invokes **one** `(pkg, method)` against **N** argument records and folds all N calls into a **single transaction**. Single-write latency (~800 µs) is at the architecture's floor and ~100% server-side (`docs/design/concurrent-merge-throughput.md` §8–§9), so the remaining multiplicative write lever is amortizing the fixed *per-round-trip* cost — parse, pov-open + `TContext` build + func lookup, commit + destruction, and the network round-trip — across many writes by paying each **once** per batch instead of per call. No new engine subsystem: `TSession::TryBatch` runs the method body N times against the same context and reuses the existing #49/#232 deferred-entry fold (`TContext::AddEffect` already Augment-merges same-key commutative effects) to emit one `TUpdate` / one commit / one `TMetaRecord`. Reply is a JSON **array** of the N per-call results. Semantics: all-or-nothing (a throw in any call aborts the batch before commit), snapshot-isolated (no read-your-writes within a batch — a write-coalescing primitive, not a transaction script), commutative ops to the same key fold while non-commutative assigns collapse last-wins. Clients: `call_batch` (python), `CallBatch` (go), `callBatch` (ts). Benchmark via `examples/agent-swarm/benchmark.py --batch N`; the `examples/wikipedia-pageviews` exact-counter self-check (`DEMO_BATCH=N`) gates correctness. Expected ~3–5× on batchable bulk-load / commutative fan-in; strict one-at-a-time latency-bound callers are unaffected (throughput, not latency). RFC: `docs/design/batched-writes.md` (PR #252). (closes #253)
- **Commutative global-merge fast-lane** (#234, behind `--tetris_commutative_fastlane`, **default off**). The single-threaded global-POV Tetris merge re-snapshotted *every* waiting child each round but promoted only one (a 2014 placeholder), so draining N queued child POVs was O(N²) re-snapshot. The fast-lane promotes **all** assertion-free (commutative `+=`/`|=`) children per round, each in its own transaction, so the one-Pusher-per-repo invariant and each child's session-id metadata (load-bearing for replication notifications) are preserved exactly; assertion-bearing RMW children keep the one-per-round discipline byte-for-byte. New reporter counter `Tetris Children Considered / Push` makes the quadratic observable: it drops from ~30 to 1.0 at 32 child POVs. Shipped default-off (PR #236). **The default-on flip was investigated and declined** (this PR): the §8.6 prerequisites were resolved — the pre-existing race the fast-lane amplifies is fixed (#237, below) and write backpressure was added (below) — but a K=24 release soak (both synchronous and pipelined, on the Tetris path) measured the flag throughput- *and* sustainability-neutral: with it on or off the run degrades identically, because the binding concurrent-write constraint is the per-write acceptance path / fast-scheduler capacity, not the merge tournament (the merge keeps up; backlog ≈1.3 children/round). So the flag stays off, available for the genuine deep-backlog regime. The benchmark (`examples/agent-swarm/concurrent_bench.py`, `run-concurrent-bench.sh`) ships with it. See `docs/design/concurrent-merge-throughput.md` §8.
- **Write backpressure on the merge backlog** (#234, `--tetris_backpressure_threshold`, default 50000; 0 disables). When a writer's POV child repo has more than the threshold of un-promoted updates backed up in its memtable, the accept path cooperatively yields its fiber (`Fiber::YieldSlow`) after committing each write until the global merge drains the backlog below the watermark. So when accept outruns promote, sustained writers degrade to a graceful slowdown that paces accept to promote, instead of the memtable growing until `bad_alloc`. A safety net for the genuine deep-backlog regime; harmless and inert under normal load (the threshold is far above the steady-state backlog).

### Fixed
- **O(W²) reduce-over-range reads — a memory-layer point-read seek accelerator** (#257). The read-side mirror of #227. A fold over a key range — `[a..b] reduce 0 + f(.k: that)`, the canonical time-travel / aggregate read — was O(W²) in fold width: each of the W per-element point reads (`TContext::operator[]`) constructed a `TMemoryLayer::TMatchPresentWalker` whose cursor started at the **head** of the layer's `EntryCollection` (an intrusive doubly-linked ordered list) and linearly scanned to the target key, so reading the key at sorted position *h* cost O(*h*) and the fold summed to ~W²/2. Confirmed three ways (black-box exponent → W^2.0; per-lookup scan-depth instrumentation growing 0→W; a `perf` profile dominated by `MatchPrefixState`/`TCore::NewState` called once per scanned entry). Disk layers were already O(1) per seek via `TIndexManager`; only the in-memory layer head-scanned, and every demo runs `--mem_sim`. Fix: an **intrusive append-only skip list** over `EntryCollection` whose express-lane forward pointers live inside each `TUpdate::TEntry` (no allocation, so it is safe on the `NO_THROW` commit path) and whose **level 0 is `EntryCollection` itself** — the upper lanes are a best-effort accelerator, so a concurrent reader that races an in-flight insert and sees a stale lane simply walks a little more of the authoritative level-0 list (never a wrong result, no new lock, same concurrency profile as the existing list). A fully-bound point read (`operator[]`/`Exists`, threaded through as an `exact_point` flag) seeks via the skip list in O(log W) to the head of the key's run; prefix / `keys`-cursor patterns keep the head-scan (the ordering comparison throws on a free-vs-concrete key, so they must). Per-entry lane height is geometric, seeded by the **index-key hash** (not the SeqNum — batched writes share one SeqNum and would collapse the lanes). The fold flips from O(W²) to O(W): a width-800 `views_total` read drops from 4.4 s to 0.11 s (debug), and per-folded-element cost goes from linearly-growing to flat. Writes stay flat (the O(log W) link is negligible against per-write sabot/commit cost). Validated by a parametrized read-scaling harness (exponent → ~W^0.9), the `wikipedia-pageviews` exact-counter self-check and `agent-swarm` (8 concurrent writers + k-hop traversal, read-back exact), `lang_test.py` (156 pass / 2 xfail), the curated ThreadSanitizer set (`context_fold`/`context_xrepo` clean), and a `memory_layer.test` seek fixture. (closes #257, 2026-06-29)
- **Allocation failure on the write-acceptance path sheds instead of crashing the server** (#250). Under memory pressure (a fixed `--mem_sim` pool running dry, or real `malloc` failing) an allocation failure on the commit path could `std::terminate` the whole `orlyi`, rather than degrade gracefully. Pre-commit failures were already graceful — `Rpc::TAnyRequest::WriteReply` wraps the handler so a `bad_alloc` thrown while *building* a transaction unwinds cleanly (the uncommitted `~TPusher` only `delete`s its copy) and is marshaled back to the client as a structured error. The one genuinely fatal path was post-commit and inside a `noexcept` destructor: `~TPusher → TRepo::AppendUpdate` makes exactly one allocating call, `TTetrisManager::Join` (a `std::map::insert` + possible player construction, run on a child repo's first un-promoted update); under pressure its `bad_alloc` escaped the `noexcept` chain → `terminate` (the `pure virtual method called`/abort in the report). `AppendUpdate` now wraps that `Join` in a `try/catch`: the update is already durable in the memory layer (reads see it) before `Join` runs, so on failure it logs and leaves the repo un-joined — the child→parent **promotion**-join is merely *deferred*, and the next `AppendUpdate` to that repo retries it (the join gate moved from a "first update only" flag to `!InTetris`, which reproduces the success-path semantics exactly — join once while there are un-promoted updates, re-join after a `PopLowest` drain — and additionally retries a previously-failed join). As belt-and-suspenders, the three `NO_THROW` commit-path destructors (`~TPusher`/`~TPopper`/`~TStatusChanger`) now catch-and-log so no allocation ever added to the commit path can silently re-introduce a `terminate`. No proactive pool-watermark shedding was added — a per-`Alloc`/`Free` gauge would regress the hot path, and the backlog-growth→OOM *precursor* is already handled by #234's `--tetris_backpressure_threshold`; this is the orthogonal "an allocation actually failed" mode. Verified by the full `lang_test.py` suite, the concurrent-writer flush-path demos (`wikipedia-pageviews` 8-writer commutative `+=`, `grc20-pov`, `recursive-variants` — all read back exact, promotion intact), and the `transaction_base`/`tetris_manager` unit tests. (closes #250, 2026-06-29)
- **Data race on a repo's in-memory update list — `AppendUpdate` vs `GetLowestUpdate`** (#237). The Tetris-merge peek (`GetLowestUpdate`) walked a repo's memtable update ordered-list while holding no lock, but a concurrent client write committing through `~TPusher → AppendUpdate` mutates that same linkage under `DataLock` — a real data race on the list (the merge fiber, or another session's peek, vs the writer). It exists on master independent of any flag; the commutative fast-lane (#234) amplifies it by promoting many children per round, so it had to be fixed before the fast-lane could default on. `GetLowestUpdate` now holds `DataLock` across the whole walk (a tag-dispatched `TView` ctor snapshots under the already-held lock to avoid re-locking the non-recursive mutex; no walker machinery re-acquires `DataLock`, and `~TView`/`AcquireCurrentMapping` take only `MappingLock`, preserving the established `DataLock → MappingLock` order, so it cannot deadlock). Verified by re-running the TSan-instrumented `orlyi` under the concurrent-writer bench: the `GetLowestUpdate` race site no longer appears. (closes #237, 2026-06-29)
- **O(N²) writes, and the dormant-merge bug cascade it uncovered** (#227). Writing N keys to a POV was O(N²): the mem→disk merge was enqueued only on the empty→non-empty edge, so under sustained writes the memory layer never drained, grew unbounded, and every write paid an O(layer-size) linear scan. The root cause was an **inverted merge-scheduler deadline** (`deadline < now` where it needed `>`) that meant `StepMergeMem`/`StepMergeDisk` *never ran* — so the entire LSM merge / disk-compaction subsystem had been dormant since the 2014-era codebase, and fixing the scheduler exposed a chain of latent correctness and stability bugs that had never been exercised. All fixed here, each gated on write-then-read-back (distinct keys *and* repeated `+=`, single- and multi-POV): **(1)** the scheduler deadline itself, so merges run and the per-write cost is flat (~2 ms/write, measured flat to 8 000 writes); **(2)** the disk compaction fold discarded its computed mutator — `TUpdate::NewUpdate`'s map constructor force-tags every entry `Assign`, so a commutative key compacted across several files became `Assign(partial)` and the latest-assign-wins read fold dropped all but one partial (a counter incremented N times read back as a fraction); now folded `Add`/`Or`/… entries keep their mutator and stay summable; **(3)** the mem-layer consolidation and **(4)** the `ReleasedUpTo` publish had the same mutator-drop / a child-drop race; **(5)** only the root POV now flushes to disk (a child's zero-`UpdateId` disk copy otherwise escaped the cross-repo dedup and double-counted), and the disk present-walker replays a key's history so a merged-to-disk counter reads its full value; **(6)** every WebSocket call leaked one fiber frame (`TJumpRunnable::Main` never freed it), capping an instance at ~`max_parallel_frames` writes; **(7)** the on-disk update index was sized by *update count* rather than *distinct sequence number*, so compaction and the fold pass reserved disk blocks they never wrote and aborted (`allocated blocks that did not get written to`) at a few thousand distinct keys; **(8)** `~TDiskLayer` let a non-shutdown exception escape a `noexcept` destructor during layer cleanup, calling `std::terminate`; **(9)** the atom-layer value serialization (`TCore::NewState`/`Remap`) had no case for the recursive-variant `SelfRef` back-reference leaf (#115) — it threw `TCorrupt` when flushing any stored recursive variant, since that traversal had never run; **(10)** the arena-note comparator asserted non-empty `Tuple`/`Record`, crashing on a stored empty record (e.g. a no-payload variant case). (8)–(10) surfaced only via the example demos once the flush ran end-to-end (`recursive-variants`, `grc20-pov`). The benchmark ([`examples/agent-swarm/benchmark.py`](examples/agent-swarm/benchmark.py)) is the perf reproduction; its verdict flips from `GROWING` to `FLAT`. Validated across all eight example demos (write-then-read), the `kit2`/indy-disk unit tests, and `lang_test.py`. (closes #227, 2026-06-24 → 2026-06-25)
- **Python client decouples the per-call recv timeout from the connect timeout** (#224). `connect()` passed a single timeout to `create_connection`, which the `websocket-client` library reuses as the socket timeout for every subsequent `recv()` — so a method reply that took longer than the (short, connect-sized) window killed an otherwise-fine call, intermittently redding CI on demos unrelated to a PR's change (e.g. a `grc20-pov` read during the `examples/*` job). The connect handshake keeps its short, retried timeout; calls now get a separate generous `recv_timeout` (default 120 s), since a reply is normally milliseconds and a long recv means a starved server, not a hung one. Retrying the call instead would be unsafe (a resent write could double-apply), so it waits rather than retries. The Go and TS clients block indefinitely on a reply and never had this timeout, so they are unaffected. (#224, 2026-06-24)
- **Client `connect()` retries with exponential backoff.** A just-started or heavily loaded `orlyi` can briefly refuse the connection or time out the WebSocket handshake before it is ready, which intermittently flaked the example drivers in CI (a `WebSocketTimeoutException` on connect). ### Changed
- **Commutative writes no longer read the current value.** A defer-safe commutative `*<[k]>::(T) OP= v` mutation compiled its LHS to `ReadOrIdentity`, which did a full flux read (`TContext::operator[]`) — but the codegen consumes only `.GetAddr()`, the value was always discarded, and an absent key already auto-initialises from the monoid identity at fold time, so the read was pure overhead. Since `TContext::operator[]` is O(pending-writes), a transaction of N commutative writes was **O(N²)**, and even a single write paid the cost. The codegen now emits a read-free `IdentityAddr` for the commutative-upsert LHS: **single writes are ~2× faster (3.6 → 1.8 ms under `--mem_sim`)** and a **batched 200-edge transaction goes 39 → 3.1 ms/edge (~12×), with scaling O(N²) → ~flat O(N)** — which unblocks bulk load. It also removes a spurious read-dependency on a coordination-free write (#49). (2026-06-26)
- **Committing a large commutative transaction is no longer O(N²).** With the per-write read gone (above), the dominant cost of a big batched write moved to the commit: `TSession::Try` registers each defer-safe commutative mutation with `TUpdate::AddEntry`, which `ReverseInsert`s it into the update's `TKey`-ordered entry collection. The deferred entries arrive in *write* order, so across several indices each insert scanned O(N) to find its slot — making a single transaction of N commutative writes **O(N²)** to commit. The entries are now sorted by `TKey` before the `AddEntry` loop, so each insert appends in O(1) (O(N log N) total); correctness is unchanged because `ReverseInsert` always finds the right slot regardless of order — only the scan length depended on it. A single-transaction bulk load now commits in **~flat O(N)**: a fresh 2 000-edge batch is ~0.33 ms/edge, holding constant from 200 to 2 000 edges (previously quadratic). This is the second and last O(N²) on the batched-write path; together with the read-elimination above, single-transaction bulk load is now linear end-to-end. (2026-06-26)
